## Critical stock fixtures

### TC-06, TC-12 and TC-11 — stock state across a single order

Use two active ingredients, A and B, with opening onHand of 10 and 8, zero reservations and no other active orders. The recipe requires 2 units of A and 1.5 units of B per portion. Submit two portions with a fresh order key. Use independent waiter and chef test accounts.

| Checkpoint | Order | A (onHand / reserved / available) | B (onHand / reserved / available) | Reservation and movement checks |
|---|---|---|---|---|
| Before creation | None | 10 / 0 / 10 | 8 / 0 / 8 | Record baseline movement and audit identifiers |
| After creation | PENDING | 10 / 4 / 6 | 8 / 3 / 5 | Two ACTIVE reservations. No consumption movement |
| After preparation | PREPARING | 6 / 0 / 6 | 5 / 0 / 5 | Both reservations CONSUMED. One new consumption movement per ingredient |
| After same-key replay and new-key repeat | PREPARING | 6 / 0 / 6 | 5 / 0 / 5 | Same-key replay returns the original response. New key returns 409. Movement and audit counts remain unchanged |
| After marking ready | READY | 6 / 0 / 6 | 5 / 0 / 5 | No additional inventory movement |

### TC-06 and TC-26 — shared ingredient across two order items

Seed ingredient A at onHand=10, reserved=0. Submit an order with two distinct items requiring 2 and 3 units of A. Expect two ACTIVE reservations keyed by their respective order item IDs and A, with 5 units reserved in total and 10 onHand. In the TC-26 race variant, both reservations are created only once. Start preparation and verify both reservations become CONSUMED, exactly two consumption movements record 2 and 3 units, and balances are onHand=5, reserved=0, available=5. Replay preparation and mark the order Ready, verifying no further deduction or consumption movements. This is the reviewer-confirmed model (D-11).

### TC-16 to TC-18 — cancellation variants

Start each variant on an isolated copy of the fixture. Save the status, onHand and reserved values, reservation states, and movement and audit IDs immediately before the request.

1. **Pending:** Cancel as a waiter and as a manager on separate fixtures. Check both reservations become RELEASED and A/B return to available 10/8 with onHand unchanged. Repeat the operation and verify the same persistent balances and no second release.
2. **Preparing and Ready:** Exercise both source states with a manager and a waiter with ORDER_LATE_CANCEL. Include a reason. Verify CANCELLED, A/B onHand 6/5, and unchanged CONSUMED reservations. Compare the new late cancellation audit event to the authenticated actor, order ID, timestamp, prior state and submitted reason. Repeat the operation and check for duplicate effects.
3. **Denied and invalid:** For each late source state, a chef and a waiter without permission receive 403. A permitted actor omitting the reason receives 422 CANCELLATION_REASON_REQUIRED. Each attempt preserves the complete baseline.

### Cancellation retry variants

Use independent fixtures for same-key/same-body, different-key/same-body, omitted-key and same-key/different-valid-body repeats. Record the first response, retry status, problem code or replay header, reservation states, stock and audit/movement counts. After each retry the order remains CANCELLED, stock and reservation state are unchanged, and there is no second release or late-cancellation audit event. The technical reviewer confirmed these responses (D-05): same key and body returns saved HTTP 200 with Idempotent-Replayed: true; different or omitted key returns 409 INVALID_STATUS_TRANSITION; same key with a different valid body returns 422 IDEMPOTENCY_KEY_REUSED.
